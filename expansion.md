# oMyImage tool expansion — playbook and page plan | | |

Started 2026-10-04 on branch `feat/tool-expansion` (cut from `main` at 8ab7967).
Goal: close the gap with **bulkpictools.com** (Nuxt, 10 locales, ~119 tool
pages, ~15.8K organic visits/month from India alone at 8 months old) by
adding roughly 70 tools, **every one shipped in en / pt / hi / ru / id in the
same batch**. The localization playbook is still `conversion.md`; this file
covers what is new: variant pages, the sitemap index, the page plan and the
research behind it.

## 1. Decisions (approved 2026-10-04)

| Question | Decision | Why |
|---|---|---|
| Per-language sitemaps like the competitor? | **Yes.** `/sitemap.xml` is now a sitemap **index** → `/sitemaps/{en,pt,hi,ru,id}.xml`. | hreflang works identically in one file or many, so this is not a ranking change. It is monitoring: Search Console, Bing and Yandex report indexed-vs-submitted **per sitemap**. Same address, so no engine needs resubmitting. |
| `/tools/compress/compress-to-50kb` or `/compress-50kb`? | **Neither — flat, exact-match**: `/compress-image-to-50kb`. | 240 indexed URLs are already flat; a 301 migration resets signals while Yandex/Bing indexing is two days old. Folder depth is not a ranking signal; a slug that mirrors the query is a (small) one. Hierarchy is expressed with BreadcrumbList and the family link strip instead. |
| Locale slugs | Unchanged rule: **pt and id translated**, **hi and ru English** under the prefix. | conversion.md §5 / §9 / §11. |
| Variants | Ordinary `tools.ts` entries with `parentId` + one-line `preset`; route stubs generated by `npm run gen:variants`. | Same reasoning as the converter generator: identical stubs are where copy-paste ships two pages on one slug. |
| AggregateRating | **Removed site-wide.** Never add to new pages. | The 4.9 / 912 on every page was not collected from users. Google treats invented ratings as spammy structured data (manual action strips rich results site-wide). |
| AI tools | Only if they run **in the browser** on commercially-safe models. | User's rule. MI-GAN (Picsart) is MIT for code **and** weights (`LICENSE-WEIGHTS` read 2026-10-04); 28 MB ONNX exceeds Cloudflare Pages' 25 MiB file cap → ship in two chunks. No ffmpeg.wasm (default build carries GPL x264); video↔GIF uses `<video>`+canvas and WebCodecs. Variants of the EXISTING server tools (remove-background, upscale) are fine — no new endpoints. |
| Pixel-size pages (resize-to-512×512 …) | **Skipped.** | Every one measured < 500/mo in every market (most 10–110). Presets inside resize-image instead. |

## 2. How a variant works

1. `src/lib/tools.ts` — an entry with `parentId: "compress-image"` and
   `preset: { targetKb: 50 },` (ONE line; the generator copies it verbatim).
   Variants show as cards in the home grid and dashboard and as rows in the
   Tools menu (add the id to a section in `lib/nav-sections.ts`) — but only
   in locales that ship them (`toolShippedIn`), so a page never links out to
   an English variant. They stay out of `relatedTools()`. Set `isNew: true`
   for the "New" badge; drop the flags once they stop being news (~2027-01).
   Tool counts (`liveToolCount(locale)`) include them, per locale.
2. The parent component accepts `preset?: …` and behaves exactly as before
   without it. TypeScript checks every generated literal against that prop.
3. `npm run gen:variants` writes `src/app/<id>/page.tsx` and one route per
   locale that ships it (`status.ts` + `<LOC>_TOOL_SLUGS`). The stub passes
   the parent's content module as `parent=` to `ToolPageShell`, which
   - merges the parent's `ui` block under the variant's — the variant renders
     the PARENT's component, whose micro-copy lives there. Without the merge
     every localized variant would silently render that component in English;
   - adds the parent to the breadcrumb (Home › Category › Parent › Variant);
   - renders `<VariantLinks>`: the family strip (parent + live variants, full
     localized names as anchor text) under the tool, headed by the parent
     module's `variantsHeading`.
4. Content: `src/content/tools/<id>.<loc>.ts`, same shape as any tool.
   `verify-build` holds every family to the converter similarity ceiling
   (0.6 Jaccard on 5-shingles, per locale) and allows at most **3** identical
   FAQ questions between any two family pages. Write each variant about its
   own job (20 KB = signatures; 50 KB = exam/government photo forms; 1 MB =
   portals that reject phone photos …), not the parent with a number swapped.

## 3. Add-a-tool checklist (there was no written one before)

1. `src/lib/tools.ts` entry (`id`, `name`, `slug` on consecutive lines —
   i18n-audit parses them with a regex), plus `TOOL_COLORS` for a new parent.
2. `src/app/<slug>/page.tsx` + component (or `npm run gen:variants`).
3. `src/content/tools/<id>.en.ts` — English inherits title/description from
   the registry `seoTitle`/`seoDescription`.
4. `src/lib/file-actions.ts` `TOOL_INPUTS` if the component uses `useHandoff`.
5. `src/lib/tool-search.ts` `TOOL_ALIASES`; `src/lib/nav-sections.ts` for a
   parent that belongs in the menus (not for variants).
6. `src/i18n/slugs.ts` — a slug in **all four** maps, even before it ships.
7. Per locale: `dictionaries/<loc>/tools.ts` (name + short description),
   `aliases.ts`, the content module, the route, and `SHIPPED_TOOLS` — same commit.
8. New Material icon → `npm run build:icon-font` (needs network).
9. New dependency → `LICENSE-AUDIT.md` rules: grep its built `dist/` for
   GPL/LGPL; browser-shipped copyleft is out.
10. Gates (conversion.md §4) + `npm run gen:variants -- --check`.
